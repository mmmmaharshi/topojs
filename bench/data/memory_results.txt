UPDATE: these numbers reflect IncrementalH1 AFTER the reducedCols/triPair
pooling optimization (src/streaming/incremental-h1.ts) -- retained per-
triangle state (previously one separate Int32Array+ArrayBuffer object and
one separate {birth,death,dim} object PER TRIANGLE, kept alive between
every push) is now packed into a few flat pooled typed arrays instead. This
is a pure storage-representation change verified to produce byte-identical
persistence pairs (the reduction algorithm itself is untouched; only what
gets RETAINED between pushes changed) -- see incremental-h1.ts's field
comment and 123/123 passing tests including the existing differential
test against StreamingHomology at every push.

BEFORE -> AFTER at windowSize=80 (the worst case, where the original 3500x
figure came from):
  sunspots:        4.864 MB -> 1.786 MB  (2.72x less)   ratio: 3484x -> 1279x
  melbourne-temp:   1.943 MB -> 0.746 MB  (2.60x less)   ratio: 1190x -> 427x
  iris (windowSize=20, its largest full window): 0.205 MB -> 0.088 MB (2.33x less)

This closes roughly 60% of the memory gap at the largest window size tested
on each dataset, consistently in the 2.3x-2.7x range across all three
datasets and both larger window sizes. It does NOT eliminate the
time/space trade-off: IncrementalH1 still retains far more state than
StreamingHomology (which keeps almost nothing), because edgeOrder and
triOrder (arrays of small JS objects, one per edge/triangle) were not
touched by this change -- see the follow-up note in docs/COMPLEXITY.md
Section 5 for why those were left alone (a much larger, riskier refactor
threaded through the entire push() method, versus this change's much
narrower footprint at the storage boundary only) and whether pooling them
too is worth the risk.

=== MEMORY SWEEP: Monthly sunspot counts (1749-1983) ===
source: SIDC/WDC-SILSO, bench/data/monthly-sunspots.csv
(process.memoryUsage().heapUsed deltas, median of 7 fresh builds per point -- noisy by nature even with GC forced, especially at small window sizes where the delta is a few hundred KB; manual GC forced before/after each build via --expose-gc)
Loaded 2820 REAL monthly sunspot readings (SIDC/WDC-SILSO, 1749-1983).
Data-driven lag (first ACF < 1/e, scanned 1..40 months): LAG=25
Embedded stream length: 2795 points (2D delay embedding, lag=25 months).

windowSize    naive_MB     incr_MB   ratio(incr/naive)
        10       0.005       0.014                2.86
        20       0.002       0.090               59.47
        40       0.004       0.326               90.93
        80       0.001       1.786             1278.85

IncrementalH1 is expected to use MORE memory than StreamingHomology at a given window size:
it keeps the previous push's full edge/triangle lists AND reduced-column state alive between
pushes (to diff against), plus the neighborsOf adjacency map -- StreamingHomology holds none of
that, it only keeps the raw window contents and discards all derived state after each push.
This is the space side of the time/space trade-off the class docstring does not currently discuss.
