Spatial-grid edge-building optimization: isolated micro-benchmark
===================================================================

WHAT THIS MEASURES
-------------------
buildRipsComplex (src/core/complex.ts) used to find all point pairs within
maxDist via a brute-force O(n^2) double loop. It now optionally uses a
uniform spatial grid (src/core/spatial-grid.ts, cellSize = maxDist) to
narrow candidate pairs before computing any distance -- see complex.ts's
docstring for the correctness argument (candidate superset, zero
approximation, byte-identical output; verified in test/spatial-grid.test.ts
via differential testing against an independent brute-force reference,
including a dedicated case with n above the threshold below).

This file isolates ONLY the edge-building step (both approaches building
the identical full {u,v,val} edge array, JIT-warmed with a throwaway run
before timing, averaged over repeated trials) to characterize the grid's
actual performance, separate from buildRipsComplex's other stages
(triangle/tetrahedra construction, matrix reduction) which this change did
not touch and which dominate total time in this repo's current benchmark
cases (see "why this doesn't move compare_ripser.py's numbers" below).

METHOD
------
2D point clouds, n points uniformly random in a box of side ~sqrt(n)*c
(c varies by regime below, controlling realized point density), fixed
maxDist=1.0, 3 timed trials per n after JIT warmup. Two regimes tested to
check whether the crossover point is sensitive to density.

RESULTS: sparse regime (c=3, box grows faster than n -- keeps edge count
low relative to n^2, mimics a low-density windowed-TDA-style point cloud)
---------------------------------------------------------------------------
n=60:    edges=12      brute=0.297ms   grid=0.982ms   speedup=0.30x  (grid LOSES)
n=150:   edges=33      brute=0.154ms   grid=0.737ms   speedup=0.21x  (grid LOSES)
n=400:   edges=69      brute=0.225ms   grid=1.225ms   speedup=0.18x  (grid LOSES)
n=700:   edges=136     brute=0.703ms   grid=0.743ms   speedup=0.95x  (breakeven)
n=1000:  edges=188     brute=1.397ms   grid=0.853ms   speedup=1.64x  (grid wins)
n=1400:  edges=266     brute=2.834ms   grid=1.300ms   speedup=2.18x
n=2000:  edges=357     brute=5.501ms   grid=2.062ms   speedup=2.67x
n=3000:  edges=518     brute=12.740ms  grid=2.996ms   speedup=4.25x

RESULTS: moderate-density regime (c=1.2 -- denser complex at the same n)
---------------------------------------------------------------------------
n=60:    edges=58      brute=0.006ms   grid=0.078ms   speedup=0.07x  (grid LOSES badly)
n=150:   edges=151     brute=0.033ms   grid=0.203ms   speedup=0.16x  (grid LOSES)
n=400:   edges=435     brute=0.230ms   grid=0.408ms   speedup=0.56x  (grid LOSES)
n=700:   edges=726     brute=0.691ms   grid=0.946ms   speedup=0.73x  (grid LOSES)
n=1000:  edges=1050    brute=1.390ms   grid=0.957ms   speedup=1.45x  (grid wins)
n=1400:  edges=1516    brute=2.848ms   grid=1.440ms   speedup=1.98x
n=2000:  edges=2190    brute=5.643ms   grid=2.006ms   speedup=2.81x
n=3000:  edges=3299    brute=12.826ms  grid=3.173ms   speedup=4.04x

A separate, much denser regime (maxDist large relative to point spread,
so nearly every pair is a true edge) was also checked at n=500/2000 and
showed the grid losing even more badly there (0.23x/0.78x) -- consistent
with the grid providing zero benefit when almost nothing is filtered out,
since candidate-narrowing has no work to save in that regime.

CONCLUSION: a real, consistent crossover around n~900-1000, essentially
the same in both density regimes tested. Below it, the grid's per-point
overhead (Map.get/set on string cell keys, small array allocation per
query) costs more than the distance computations it avoids. Above it, the
O(n) grid construction plus O(3^dims) candidate cells per point starts
winning over O(n^2) brute force, and the win grows with n as expected.

DECISION
--------
buildRipsComplex now gates the grid behind GRID_MIN_N = 1000 (src/core/
complex.ts) -- a single, density-agnostic constant set just above the
measured crossover, chosen deliberately simple over an adaptive density
estimate since both regimes tested crossed over in the same neighborhood.
Below GRID_MIN_N, buildRipsComplex always uses brute force, exactly as
before this optimization existed -- no regression is possible for n below
the threshold, by construction.

WHY THIS DOESN'T MOVE compare_ripser.py's OR benchmark.ts's NUMBERS
---------------------------------------------------------------------
Every real-data case in this repo's other benchmarks uses n=60-400 points
(bench/compare_ripser.py) or windowSize=5-80 (bench/benchmark.ts's
streaming comparisons, via StreamingHomology's naive buildRipsComplex
rebuild on every push). All of these are below GRID_MIN_N=1000, so the
grid path is never taken by any currently-benchmarked case in this repo --
this is not a bug, it's the threshold correctly protecting small-n cases
from the grid's measured overhead. The optimization's real, verified
benefit (correctness-checked via differential testing, performance-checked
here) applies to larger point clouds than this repo currently benchmarks
on; it is reported honestly as such rather than claimed as a win on
existing benchmark numbers it does not actually move.

Reproduce: the exact scripts used are not checked into this repo (ad hoc
isolated micro-benchmarks, not part of the `npm run bench` harness since
they test an internal implementation detail of buildRipsComplex rather
than a user-facing engine comparison) -- the method above is complete
enough to reproduce directly against src/core/spatial-grid.ts.

===================================================================
RE-RUN after finding #14 (Map<string,...> -> Map<bigint,...> grid keys)
===================================================================

The above numbers were measured against the original string-keyed grid
(Map<string, number[]>, keys via coords.join(',')). A later codebase
audit replaced that with BigInt-packed keys (see src/core/spatial-grid.ts's
class docstring) specifically because string-key overhead was flagged as
a likely cause of the crossover sitting as high as n~900-1000. This
re-run checks whether it actually moved -- deferred at the time of that
fix as "a separate task from fixing the two correctness-adjacent-risk/
memory issues" it addressed.

METHOD: identical to above (same point generator shape, maxDist=1.0, two
density regimes), but 25 timed trials per n (up from 3) with a 5-call JIT
warmup and a median instead of a mean, after the original 3-trial method
proved noisy enough at small n to occasionally invert the expected
ordering. Also added finer n steps (400-1000 in steps of 50-100) around
the new crossover, since the original steps (400, 700, 1000) were too
coarse to localize it.

CONCLUSION: the crossover moved from ~900-1000 down to ~600-650 in both
regimes -- a real, consistent effect (not noise: the moderate-density
regime is a bit choppier right around the new crossover, n=700 dips back
under 1x there, but the trend on both sides is unambiguous). Consistent
with the original fix's own stated rationale: removing per-point
string-allocation-and-hashing overhead was expected to lower exactly
this threshold.

DECISION (superseded, see UPDATE below): initially left GRID_MIN_N at
1000, unchanged, since it also gated a second, unrelated decision --
complex.ts's dense-vs-sparse edgeIndex memory strategy (finding #16) --
that had never been benchmarked at a lower threshold, and retuning the
shared constant would have silently moved that too.

UPDATE: rather than accept that as a permanent trade-off, complex.ts's
single GRID_MIN_N was split into two independent constants:
GRID_MIN_N (edge-building, this benchmark) and EDGE_INDEX_DENSE_MAX_N
(triangle/tetrahedron edgeIndex memory layout, finding #16). Each now
governs only the decision it was actually benchmarked for:

  - GRID_MIN_N lowered to 700 (just above the new ~600-650 crossover
    measured above), capturing the previously-unclaimed speedup for
    n in [700, 1000).
  - EDGE_INDEX_DENSE_MAX_N left at 1000, exactly as originally verified
    for finding #16 -- completely unaffected by this change, since it is
    no longer coupled to GRID_MIN_N.

This means n in [700, 1000) is now a new combination -- grid-accelerated
edge-building feeding into the dense Int32Array edgeIndex branch -- that
never occurred while both were one threshold. Covered by a new
differential test in test/spatial-grid.test.ts ("...IN THE
GRID_MIN_N..EDGE_INDEX_DENSE_MAX_N GAP...", n=800, maxDim=3, checked
against a direct distance recomputation). Full test suite (168 tests)
and lint/typecheck pass unchanged.
