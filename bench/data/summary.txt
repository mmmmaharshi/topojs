TopoJS Incremental-H1 Speedup Analysis — Real-Data Benchmarks Only
====================================================================
Date: 2026-07-10

All synthetic-data benchmarks (i.i.d. random point clouds used for
scalability/comparison claims, and the earlier i.i.d.-random incremental-H1
speedup benchmarks) have been removed from this repo, along with their
output data, per an explicit decision to keep only benchmarks run against
real, externally-sourced data. What remains below are the three real-data
speedup benchmarks for the v3 incremental-geometry change to IncrementalH1
(src/streaming/incremental-h1.ts) versus the Phase A naive baseline
(StreamingHomology). All three now run from one parameterized harness,
bench/benchmark.ts (dataset registry keyed by name), rather than three
separate near-duplicate scripts -- run all with `npm run bench`, or one
with `npm run bench -- <name>`.

Axis 1: Incremental H1 (v3) vs Phase A naive, REAL data — monthly sunspots
  Data: monthly sunspot counts 1749-1983 (2820 real months, SIDC/WDC-SILSO,
  bench/data/monthly-sunspots.csv) -- the same series used for the
  correctness/scientific validation in bench/real-data-validation.ts, here
  repurposed for a SPEED comparison instead. 2D delay (Takens) embedding,
  lag=25 months selected via data-driven ACF<1/e rule (not tuned to this
  result). Windowed and split into 6 disjoint chunks (paired trials); each
  chunk timed on both engines. windowSize=40, maxDist=0.15.
  Result: geometric mean speedup 1.91x (95% CI 1.67x-2.19x), t(5)=9.2,
  significant despite the small N=6 (only one real series exists to chunk).
  Consistent across independent runs (1.91x and 1.93x).
  Honest negative/nuanced finding: mean re-reduced fraction stayed ~99% on
  real data, essentially the SAME as the earlier i.i.d.-random benchmarks
  (since removed) -- the hypothesis in the IncrementalH1 docstring that real
  temporal locality would let the prefix-caching mechanism itself skip more
  re-reduction was NOT confirmed at this configuration (windowSize=40,
  lag=25). The v3 incremental-GEOMETRY speedup (this axis's actual measured
  ~1.9-2x) holds up fine on real data regardless -- that part of the
  mechanism doesn't depend on prefix-caching paying off. Script:
  bench/benchmark.ts (npm run bench -- sunspots). Re-run before citing.

Axis 2: Incremental H1 (v3) vs Phase A naive, REAL data — UCI Iris
  Data: UCI Iris, 150 real physical measurements (sepal/petal L+W, 4D),
  streamed in ORIGINAL recording order (50 Setosa, 50 Versicolor, 50
  Virginica) -- src/data/realworld-datasets.ts, source archive.ics.uci.edu.
  Deliberately a DIFFERENT kind of real structure from Axis 1's sunspot
  time series: no temporal autocorrelation, instead an abrupt real
  structural change (species boundary) partway through the stream, plus 4D
  not 2D. windowSize=20, maxDist=0.35 (per-column min-max normalized).
  Caveat stated up front (unlike Axis 1's 6 disjoint chunks): only 150
  points exist, so there is exactly one real ordering -- the 10 "trials"
  here are REPEATED TIMED RUNS of that SAME stream, capturing measurement/
  JIT noise only, not additional real-data diversity. Said plainly in the
  script header, not glossed over.
  Result: geometric mean speedup 1.34-1.35x (95% CI ~1.05x-1.72x), t(9)=2.3-2.7,
  significant at p<0.05 in both independent runs, but visibly weaker/noisier
  than Axis 1 (small window=20 leaves less O(k^2)/O(k^3) waste to cut, and
  2 of 10 repeats came in BELOW 1x, most likely JIT warmup on the first
  timed call rather than a real regression -- shown in the raw table, not
  hidden). Re-reduced fraction: 98.9%, same pattern as every other axis --
  further evidence the prefix-caching mechanism itself stays saturated
  regardless of data type; only the v3 geometry-construction change carries
  the measured speedup, consistently, across real time series and real
  class-structured data. Script: bench/benchmark.ts (npm run bench -- iris).
  Re-run before citing.

Axis 3: Incremental H1 (v3) vs Phase A naive, REAL data — Melbourne daily
  min temperatures
  Data: 3650 real daily minimum temperature readings, Melbourne Australia,
  1981-1990, Bureau of Meteorology (public mirror, downloaded by the user
  and placed at bench/data/daily-min-temperatures.csv -- an actual
  downloaded file, not hand-typed or synthesized). A third, distinct real
  regime: much longer (3650 vs 2820 sunspot months / 150 iris rows),
  noisier daily weather data with its own yearly seasonal cycle plus real
  day-to-day variation. 2D delay embedding, lag=46 days via the same
  data-driven ACF<1/e rule (not tuned). windowSize=45, maxDist=0.15, split
  into 8 disjoint chunks (paired trials), same design as Axis 1.
  Result: geometric mean speedup 1.65-1.67x (95% CI ~1.42x-1.95x), t(7)=6.4-6.6,
  significant across two independent runs. Sits between Axis 2's iris
  result (1.34x, small window) and Axis 1's sunspot result (1.91x) --
  consistent with the complexity argument: this window (45) is bigger than
  iris's (20), landing speedup in between.
  Re-reduced fraction: 99.6%, again consistent with every other axis --
  third independent real-data confirmation that the whole measured gain is
  the v3 geometry-construction change, not prefix-caching. Script:
  bench/benchmark.ts (npm run bench -- melbourne-temp). Re-run before citing.

Cross-axis summary: v3 incremental-geometry speedup measured at 1.3x-1.9x
(geometric mean) across three independently real, structurally different
datasets (solar time series, biological class-structured data, daily
weather time series), all statistically significant despite small chunk
counts (N=6-10 per axis, the practical limit of chunking a single real
series). Re-reduced fraction stays 98.9-99.6% in every real-data axis,
consistently indicating the entire measured speedup comes from the v3
geometry-construction change (skipping full O(k^2)/O(k^3) rebuild), not
from the prefix-caching / reduction-skipping mechanism.

Axis 4: Scaling sweep — does the growth RATE differ, not just a constant
  factor? Axes 1-3 above each use ONE fixed window size per dataset, so a
  1.3x-1.9x speedup could in principle just be a constant-factor win (same
  big-O, smaller constant) rather than the claimed different asymptotic
  class (naive full O(k^2) edges + O(k^3) triangles rebuild vs incremental
  O(k) new-point distances + O(deg(new)^2) new triangles). This axis tests
  that directly: for each dataset, time BOTH engines across a RANGE of real
  window sizes (same data, same maxDist, only k varies), then fit a log-log
  growth-rate exponent p to each engine's time-vs-k curve (time ~ C*k^p).
  Method: bench/benchmark.ts --scaling <dataset> (npm run bench -- --scaling
  <dataset>); disjoint real-data chunks per window size (paired trials, same
  design as Axes 1/3), 6-10 trials per size depending on how much real data
  the dataset has to spare. Raw output: bench/data/scaling_results.txt.

  Sunspots (windowSize 10/20/40/80, 6 trials each): naive p=2.07-2.09,
  incremental p=1.84-1.87. Speedup widens with window size (1.28-1.29x at
  k=10 -> 1.93-1.98x at k=80) -- this is the CONFIRMING result: on this
  dataset the incremental engine measurably grows slower than the naive
  rebuild, not just a fixed ratio.

  Melbourne temps (windowSize 10/20/40/80, 6 trials each): naive p=1.98-2.09,
  incremental p=1.87-1.93 -- close to each other, not clearly separated.
  Speedup is noisy rather than monotonically widening (1.28x, dipped to
  0.98x-1.12x at k=20, back up to 1.65-1.98x at k=40, 1.65-1.68x at k=80).
  Honest reading: on this dataset, at these window sizes, most of the
  measured time in BOTH engines is spent in the shared reduction step (which
  Axes 1-3 already showed stays ~99% re-reduced regardless of engine), so
  the two curves track each other more closely than on sunspots -- the
  construction-cost win is present (naive slope still nominally higher) but
  smaller and noisier here than the sunspots axis shows.

  Iris (windowSize 5/10/20, 3 trials each -- only 150 real points total, so
  fewer/smaller trials than the other two, and all timings are sub-15ms,
  where JIT/measurement noise is a large fraction of the signal): naive
  p=1.83-1.88, incremental p=2.13. Speedup SHRINKS with window size here
  (1.52-1.62x at k=5 down to 1.08x at k=20) -- the inverse of the sunspots
  result. Reported plainly rather than dropped: this is the dataset with the
  least statistical power (fewest trials, smallest absolute times, same
  caveat already stated for Axes 1-3's Iris numbers), so it is the least
  reliable of the three, but it is a real disconfirming data point at this
  configuration and is not excluded from this summary.

  Cross-dataset reading: the complexity argument (incremental should grow
  slower than naive as window size increases) is clearly confirmed on one
  of three real datasets (sunspots), ambiguous/roughly-tied on a second
  (Melbourne temps), and inverted on the third, least-powered one (Iris).
  The FIXED-window speedup claims in Axes 1-3 (1.3x-1.9x, each statistically
  significant on its own terms) stand independent of this axis. What this
  axis adds honestly: the speedup is not uniformly explained by a widening
  asymptotic gap across all real data tested -- on some real datasets/window
  ranges it looks close to a constant-factor win instead. This is a genuine
  open question for further work (larger window-size ranges, more trials,
  and/or a formal complexity proof -- see project punch list), not a
  settled result. Re-run before citing; see bench/data/scaling_results.txt
  for full raw tables. A precise, code-derived explanation for WHY the
  results are mixed (not just that they are) is in docs/COMPLEXITY.md --
  short version: the naive baseline's own triangle construction is also
  data-dependent (bit-set intersection, not a flat O(k^3)), so the two
  engines are closer to each other in complexity class than the headline
  numbers above suggest, once that and real-data density are both
  accounted for precisely.

Axis 5: Memory sweep -- the speed win is a TIME/SPACE trade-off, not a
  strict improvement. IncrementalH1 keeps the previous push's full edge/
  triangle lists AND reduced-column state alive between pushes (the whole
  mechanism the speedup depends on); StreamingHomology discards everything
  but the raw window contents after every push. Measured directly
  (`npm run bench -- --memory <dataset>`, median of 7 fresh-instance heap
  deltas per point, --expose-gc forcing collection before/after each to
  reduce noise; bench/data/memory_results.txt):
    sunspots:    4.2x (k=10) -> 24.8x (k=20) -> 204x (k=40) -> 3484x (k=80)
    melbourne:   2.7x (k=10) -> 15.0x (k=20) -> 142x (k=40) -> 1361x (k=80)
    iris:        2.6x (k=5)  -> 4.7x (k=10)  -> 24.1x (k=20)
  Consistent across all three real datasets: the memory ratio grows sharply
  with window size, reaching ~1300x-3500x at the largest window sizes
  tested. This was not measured or discussed anywhere in this repo before
  now. It does not invalidate the speedup claims in Axes 1-4 (time and
  space are different resources), but it means IncrementalH1 is a genuine
  trade-off, not a strict win -- fine for one or a few concurrent windows,
  a real limitation for many-concurrent-window use cases (e.g. one window
  per sensor across a large fleet), where StreamingHomology's near-zero
  retained state may be preferable despite its slower per-push time. See
  docs/COMPLEXITY.md Section 4 for the full writeup.
