REDUCED VIETORIS-RIPS COMPLEX (Koyama, Memoli, Robins, Turner, "Faster
computation of degree-1 persistent homology using the reduced Vietoris-Rips
filtration", arXiv:2307.16333, 2023/2024) -- implemented as a new engine,
computePersistentHomologyReduced (src/core/homology-reduced.ts), H0+H1 only.

Measured via bench/reduced-vr-comparison.ts, comparing
computePersistentHomology(points, dims, maxDist, 1) [existing standard
engine, restricted to return H0+H1 pairs, but which still builds the FULL
2-skeleton internally -- 2-simplices are needed to compute which edges die,
regardless of the maxDim argument; buildRipsComplex does not gate triangle
construction on maxDim] against computePersistentHomologyReduced [new engine,
builds only the reduced complex's much smaller triangle set]. This is the
correct, fair baseline: both engines return the exact same H0+H1 barcode,
and the comparison isolates exactly the cost this technique targets.

Real data only (per AGENTS.md's real-data-only benchmark policy): UCI Wine
(178x13D), UCI Sonar (208x60D), UCI Seeds (210x7D), UCI Iris (150x4D, raw cm
scale), and the Jazz musicians collaboration network (198 nodes, graph
Laplacian 3D embedding, already vendored in bench/data/jazz.csv for
bench/benchmark.ts). Two maxDist values per dataset (sparser / denser).
Timing via median of 12 trials (3 warmup) for the fast datasets; the Jazz
"denser" case is genuinely slow at baseline (~9.5s/call, exactly the crowded
regime this technique targets) so it uses fewer replicates (documented per
case below) to keep total measurement time practical -- correctness was
still checked on every run.

PATTERN: the speedup tracks triangle-count reduction almost exactly, and
both scale up sharply with density. At maxDist values sparse enough that the
full complex has few or zero triangles anyway (Wine 0.25, Seeds 0.15), the
reduced engine's own per-edge lune-scan (O(n) per edge just to check for lune
membership, before any triangles even get built) is pure overhead with
nothing to pay it back, so it's mildly SLOWER than baseline (0.3-0.8x) --
this is honest and expected: the technique's benefit is entirely in the
avoided triangle construction/reduction cost, so it can't win when that cost
was never going to be large. At denser, more topologically realistic maxDist
values, the reduced complex shrinks the triangle count to 2-14% of the full
complex's, and wall-clock speedup ranges from about 4x to 43.5x, with the
biggest wins on the biggest/densest real complexes (Jazz, Iris denser) --
exactly where this matters most in practice, since those are the cases where
the standard engine's cost was becoming a real problem.

MEMORY: heap-delta measurements (process.memoryUsage().heapUsed, forced GC,
median of several repeats -- same method as bench/swap-reduction-comparison.ts)
came back too small and noisy to report meaningfully at these dataset sizes
(deltas in the 0.001-0.05MB range, frequently negative, i.e. within V8's own
GC/measurement noise floor -- see bench/benchmark.ts's memory-sweep
docstring for the same caveat on this measurement method). The real memory
story here is structural, not measured via heap delta: fewer triangles means
fewer ColumnStore blocks allocated and fewer DenseWorkingCol XOR operations
during H1 reduction, which is a direct, mechanical consequence of the
triangle-count numbers above, not a separate claim needing its own
measurement.

CONCLUSION: computePersistentHomologyReduced is an exact H0+H1 engine --
the same H0+H1 barcode as the standard engine across the real-data cases
above and the differential suite. The opt-in collapsed path was also run on
all 10 real-data cases with `--collapse`; every collapsed barcode matched
the standard barcode. The per-case collapsed measurements below come from a new
run of the same benchmark with the current normalized-Iris protocol. Do not
compare their Iris timings with the historical raw-scale table above.

ON-DEMAND DISTANCE RUN: the reduced engine was rerun after replacing its
full squared-distance matrix with on-demand squared-distance calculations.
All 12 default and 12 collapsed configurations matched the standard H0+H1
barcode. Edge and triangle counts were unchanged. The added real sunspots
cases were:

  Monthly sunspots maxDist=0.005: n=2795, reduced 27.755ms, 2438 edges,
    1138 triangles, old reduced matrix bytes removed 29.80MiB
  Monthly sunspots maxDist=0.02: n=2795, reduced 130.952ms, 31695 edges,
    29019 triangles, old reduced matrix bytes removed 29.80MiB

Those two timings are single runs from the benchmark above, not the paired
smoke check further down, which is a separate three-trial measurement and
reports different (and for maxDist=0.02, slower) numbers. Both are kept
because they measure different things; neither is the other one's baseline.

These bytes describe only the removed distance matrix. The reduced engine still
allocates its dense edge index.

Wall-clock timings moved in both directions across the real datasets, so this
run does not claim a universal time speedup. A paired sunspots smoke check
used the same lag-25 delay embedding, three trials, and identical counts. The
old matrix implementation took 42.146ms at maxDist=0.005 and 207.889ms at
0.02. The on-demand implementation took 22.535ms and 147.108ms. The
implementation removes the O(n^2) distance-matrix allocation; the expected
memory benefit grows with n. The dense edge index remains. Heap-delta
measurements remain noisy and are not a release-quality memory claim.

The reduced engine is exposed through
`advanced.computePersistentHomology` with `engine: "reduced"`. Its
`collapse: true` option is opt-in. The default
reduced path remains unchanged. The reduced engine computes H0+H1 only;
H2 requires another engine.
